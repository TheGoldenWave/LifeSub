# 测试与审查策略

本文是项目关于测试先行、验收证据和代码审查的单一事实源。

## 核心原则

1. 验证方式必须匹配变更风险和可观察结果，不以新增测试数量衡量质量。
2. 行为、数据、安全和接口契约变更采用 TDD：先观察目标测试因当前缺陷正确失败（RED），再做最小实现并验证通过（GREEN）。
3. 纯视觉、文档、配置和生成物变更不得为了形式合规而制造无意义单元测试；必须提供可重复、能发现目标缺陷的对应证据。
4. 混合变更拆分验证：行为部分走 RED/GREEN，视觉或产物部分走截图、构建或结构化检查。
5. 自动化测试不能替代真实环境验收。

## 变更类型与验证方式

| 变更类型 | 首选验证 |
|---|---|
| 行为、业务逻辑、状态机、错误处理 | RED/GREEN 单元或集成测试；相关回归 |
| 数据、事务、迁移、证据来源、恢复 | RED/GREEN 集成测试；故障注入；持久化/重启验证 |
| 安全、权限、身份、API/DTO、并发 | RED/GREEN 契约或负向测试；相关 feature 构建 |
| 纯视觉、响应式、字体、对比度、溢出 | Playwright/截图；多视口；DOM/可访问性检查 |
| 交互可访问性 | 浏览器交互；焦点/键盘/ARIA 检查；必要时组件测试 |
| 文档、文案 | lint、链接、术语和事实核对；渲染预览 |
| 配置、manifest、生成物 | 解析/Schema、生成 diff、构建或 smoke test |
| 性能与资源 | 基准或量化采样；明确阈值 |
| 纯重构 | 重构前后现有回归保持绿色；必要时补契约测试 |

## RED/GREEN 边界

行为、数据、安全、身份、来源、事务、并发和公共接口变更必须看到有效 RED。RED 必须因目标缺陷失败，不能是错误 mock、语法错误或环境未启动。

纯视觉、文档、配置、元数据和生成物不强制新增失败单元测试，但必须提供本表规定的可重复证据。已有测试能复现缺陷时优先复用。

## Spec 要求

每项验收条件应声明：变更类型、风险级别、是否要求 RED/GREEN、验证层级、通过标准、必需环境和证据路径/命令。不得笼统写“所有改动 TDD”或“补测试”。

## 审查规则

- Reviewer 先判断验证手段是否匹配变更类型，再判断证据是否充分。
- 纯视觉、文档或配置变更没有新增单元测试，本身不是 finding。
- 应指出具体缺失的风险证据：行为缺 RED/GREEN，UI 缺多视口/可访问性，配置缺解析/构建/产物核验。
- 不得为了覆盖率数字增加只验证 mock 的测试。
- Critical 必须为 0；其他严重级别按项目 `AGENTS.md` 处理。

## 门禁

- Tier 1：当前 Task 的 focused 验证。
- Tier 2：focused + related tests、格式、lint/clippy、类型/构建和 diff 检查。
- Tier 3：Task 完成时运行全量测试和目标 build；UI 加 Playwright/多视口，原生能力加安装包/目标设备验收。

覆盖率阈值由 feature spec 明确；项目不设置脱离上下文的统一硬门槛。skip/ignored 必须有原因和触发方式，不能隐藏失败。
