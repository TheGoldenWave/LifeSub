# 会议 ASR 与 Qwen-Audio-Agent：LifeSub 的启示与开发方向校对

> 日期：2026-09-11；类型：产品与技术综合分析。本文完成方案校对，不代表启动功能开发。0.2.2 保持既有 S1–S4 边界，后续主题为待验证建议，不承诺版本日期。

## 1. 核心判断

### 用户确认后的定义补充（2026-09-11）

为忠实还原录音所做的内容治理属于 LifeSub，包括语义热词纠错、说话人归属和基于目标范围的背景对话过滤；可以引入 LLM/受约束 Agent。它不等于上层项目解释或长期 Memory 治理。

用户已确认将“校正转写”和“目标对话视图”合并为唯一「AI 校正」版，在设置中勾选处理维度；不采用三层用户模型，不按维度持久化完整中间文本。保留原始 ASR 供核对，过滤以可追溯的修改/排除记录表达。维度建议、设置作用范围与存储原则见 [产品定义](../../../product-brief.md)。下文各研究切片是同一能力的验证拆分，不是独立产品版本。

LifeSub 应把“可靠记录、找回并核对原话”作为近期产品重心。会议 ASR 文章强化了这条路线：转写的价值在于内容、时间、说话结构与不确定性共同构成可核对的记录。Audio-Agent 文章则提醒我们，采集、处理、呈现和上层执行各有节奏，不能让慢任务阻塞核心体验。

两篇文章都不构成立刻替换模型或把 LifeSub 改造成语音助理的理由。优先吸收质量标准、职责拆分和诚实状态反馈；保留原始音频、精确来源、模型身份、Receipt、不可变 Revision 与权限边界。下一步仍是 0.2.2 稳定化，其后通过真实找回失败选择一个主要产品主题。

## 3. 会议 ASR 文章：改变质量目标，谨慎选择实现

### 3.1 最值得采纳的是“结构化且克制”

文章指出远场、混响、噪声、多人重叠、中英混杂和术语常同时发生。错误不只是错一个字，还可能让下游把承诺归错人、把否定听成肯定，或者引用不存在的话。LifeSub 的成功标准应从“生成了文本”进一步走向“用户能核对关键原话”。

| 文章方向 | LifeSub 的产品价值 | 适配方式与边界 |
|---|---|---|
| 时间戳与结构化转写 | 搜到后能直接回听 | 保留 source/chunk 时间锚点；模型生成的时间还须检查范围和对齐质量 |
| 多说话人、重叠 | 避免多人语句混为一人陈述 | 匿名 speaker 分段先行；允许时间重叠；不能为了顺序显示强制抹掉重叠 |
| 长上下文与术语 | 跨片段一致，提升检索命中 | 只用获授权的有界上下文，记录上下文来源与版本；不能以项目常识补出没说的话 |
| 表达不确定 | 让用户知道哪里值得核对 | 区分模型评分、系统质量提示、人工标记；无评分时写未知，不生成伪置信度 |
| 内生声学能力 | 减少流水线级联误差 | 作为候选技术路线评测，不删除当前有效的 VAD、对齐或采集保护 |

“已提交 ASR”仍是模型对音频的解释，不等于绝对事实。保留原始音频才允许日后纠错；一个更强模型也不能保证不会幻觉。界面需要让原始录音、模型原始转写、人工修订和其他派生内容各自可辨认。

### 3.2 不要把来源、匿名说话人与真实身份混为一谈

系统音频可能包含多人；麦克风也可能录到多人或扬声器回声。`microphone/system_audio` 是来源，不是人物。会话内 Speaker A 是聚类标签，不是“张三”，也不默认等于下一场会议的 Speaker A。声纹匹配是再上一层，须独立授权、校验误识率并允许人工纠正。

建议先验证匿名说话结构是否显著降低回听成本，再决定是否引入 CAM++ 等身份匹配。产品定义中的“谁在什么时候说了什么”作为目标保留；当前交付承诺应准确表达为“什么时候、哪个音频来源、说了什么，能回到原音频核对”。

### 3.3 长上下文与物理分片不冲突

不可变音频分片用于可靠落盘和恢复，不要求模型只能独立理解每一个分片。未来可以在内存中组装有界跨片段窗口，附带前文转写或词典条件，输出仍映射回全部输入 chunk 和精确范围。若跨 chunk 输出超出现有发布契约，必须单独设计，不能塞进 0.2.2。

建议比较三条路线：现有模型基线、现有模型加受控上下文/派生校对、可运行的会议专用或统一结构化模型。用同一音频、设备、评分规则比较质量、等待时间和资源，再选最小有效方案。当前不建议自行训练 foundation model，也不以“端到端”作为产品卖点替代结果评测。

## 4. Audio-Agent 文章：学习非阻塞与状态语义，不复制整个助理

文章的“并行”主要指对话与后台执行不互相阻塞；其 owner 级 FIFO 仍将普通请求串行送入固定后台会话，部分长任务才进一步委派。因此不能把它理解为无限并行推理，也不能照搬一条全局 FIFO 到 LifeSub，让重转写拖住采集或状态查询。

| 文章机制 | 对 LifeSub 的启示 | 不应照搬之处 |
|---|---|---|
| 前台轻量、后台处理 | 录音、停止和浏览不等待 ASR 完成；有界队列和资源优先级保护采集 | 不新增 Gateway、多 Agent 或八工具前台来重做已有 Core/Job |
| 受理后立即返回 | 分清已受理、排队、处理中与已发布 | 不能把乐观可用性快照当成功，也不能跳过持久化或授权校验 |
| 任务 ID、匹配结果回流 | 重试、取消、晚到结果绑定准确任务与 generation | UI 文案不能替代已有 Job fencing 和原子发布 |
| 取消确认、重启诚实失败 | 请求取消不等于已经停止；不能显示伪恢复 | LifeSub 已有安全重放机制，不能照搬重启后一律失败而丢弃可恢复工作 |
| 择时播报 | 长任务结束不夺焦点、不打断当前录音操作 | 当前无 TTS，不为“播完才算投递”新增播放系统 |
| 最终 ASR 与整理意图分开 | 保留原文和派生意图，后者不得篡改前者 | “最终 ASR 是唯一事实”只适用于其交接约定；LifeSub 的原始音频仍是核对依据 |
| 四层上下文与精确改写 | 规则、偏好、模型推断的权限应分开 | Markdown 单处替换不能替代 append-only Evidence；不在 LifeSub 自动写长期 Memory |

未来集成中还应区分“处理完成、结果已保存、通知已展示、用户已核对、行动已执行”。LifeSub 的 ASR 成功止于有效 Evidence 原子发布，用户是否看过不是其成功条件。Malow 的 Review 接受也不等于 GoldenWave 已完成知识治理。

### 记录的语音不能自动成为命令

会议中有人说“把这份资料发出去”，不等于当前用户授权 Agent 发送资料；转写里出现“忽略之前的规则”也只是被记录的内容。若未来增加执行入口，应由用户显式选取片段并提出任务，接收方保留原文引用和独立指令，按自己的权限规则处理。录音权限不自动包含云处理、Agent 读取、行动执行或声纹授权。

## 5. 产品分工与用户体验

LifeSub 独立可用的核心任务是“记录 → 找回 → 回听核对 → 引用或导出”。会议是优先验证的高价值场景，不必把产品收窄成只做会议纪要。用户不必理解三个产品架构才能完成这条路径。

| 责任 | 所属产品 | 应交付的结果 |
|---|---|---|
| 原件、ASR、Revision、检索、音频权限 | LifeSub | 可定位、可修订、可授权的 Evidence |
| 项目解释、候选、决定与行动、人工 Review | Malow 或等价 Review 入口 | 引用 Evidence 的解释/行动与审核回执 |
| 正式长期事实、知识、人格上下文 | GoldenWave | 经治理的 Memory |

近期交互应先解决“能不能录、录到了没有、转写到哪里、哪里失败、如何核对”。未来结构化转写可以在详情中提供匿名 speaker 和不确定片段筛选，但不能将尚未实现的功能先作为可操作入口。

9 月 9 日已发现的恒定“ASR 待接通”、可选模型被计作需处理、声纹注册说明、词典生效范围与润色/复制差异，应在 S2 中校正文案或现有状态投影。若要新增可审计的词典校对、润色 Revision 或质量标记持久化，则转入后续专项。9 月 3 日已完成的固定控制、搜索导航、滚动、关闭保护和诊断复制不重复开发。

### 6.1 0.2.2：既有 S1–S4 保持封顶

| 阶段 | 本轮校对后的重点 | 完成线 |
|---|---|---|
| S1 信息组织 | 围绕当前录音模式、当前模型与诊断组织；先盘点已完成 UI | 用户能找到必要条件，不增加设置实体 |

| S4 性能基线 | 固定设备/样本/构建，测启动、首帧、RTF、RSS、取消受理与完成延迟 | 提供可复跑报告；不以性能测量为由改模型或引擎 |

会议质量研究可独立在文档/离线样本层准备，不增加 S4 或 0.2.2 的发布硬门槛。涉及 schema、helper 拓扑、Evidence 图、新事件/发布语义的提案，继续后置。

### 6.2 后续版本：用失败原因选择主题，不先绑定 0.3/0.4

| 待验证切片 | 触发证据 | 最小结果 | 停止或转向条件 |
|---|---|---|---|
| R1 会议质量与找回基线 | 用户有真实回查需求 | 标注样本与失败分类，比较现有模型 | 主要失败来自入口或命名时先改找回体验 |
| R2 转写质量专项 | 术语/漏词/说话归属是主要失败 | 从上下文、词典派生、匿名 speaker 或候选模型中选一项 | 关键错误不改善或资源成本不接受则不替换 |
| R3 双源重复专项 | 扬声器回灌造成重复、误归属 | 比较原始双源与 AEC/融合候选，原件始终可访问 | 无显著收益或误删独立发言则维持原始视图 |
| R4 一条消费者闭环 | 独立找回成立，用户有持续 Review 需求 | 一个获授权消费者完成引用、回听、Review 与状态检查 | 授权/撤回无法闭环则不扩大宿主数量 |
| R5 存储与生命周期 | 增长或清理成本已妨碍持续使用 | 保留、删除、恢复、派生物与缓存边界明确 | 可用空间风险高时可优先于 R2–R4 |

R 编号是本分析的研究/立项切片，不是已有 Task 编号或强制串行开发排期。建议先 R1，再据数据选一个主要实现主题；R4 以前至少明确适用的访问与撤回规则。实时 preview 只在等待时间确实影响使用时立项；全天采集、跨设备、多模态、硬件继续按开放问题 Gate 推进。

## 7. 最小研究与验收方法

建议产品负责人负责场景与成功任务，开发负责固定执行身份和结果导出，QA 负责盲评、时间锚点与失败归因；这是责任建议，尚未委派或启动实验。

第一轮可用自愿授权的 6–10 场会议建立探索集，覆盖近场/远场、耳机/扬声器双源、噪声、中英术语、多人重叠和至少 30 分钟连续录音。增加静音/非语音负例。对关键片段人工标注，听不清处标未知；将调参样本与保留评测样本分开。小样本只用于确定问题方向，不能包装成全场景准确率。

| 维度 | 记录方法 | 决策用途 |
|---|---|---|
| 文本 | 中文 CER、英文 WER 分开；固定数字、标点和中英混合评分规则 | 判断真实准确度，不混用不兼容百分比 |
| 关键事实 | 人名/术语/数字/否定词错误数及人工原因 | 防止整体字错率掩盖重要误导 |
| 无语音幻觉 | 静音/噪声中新增内容、无法由声音支持的关键陈述 | 评估生成克制；单独列错例 |
| 说话结构 | 匿名 speaker 错归、重叠漏失；有标注时使用 DER 并说明重叠评分规则 | 不将低字错率误当身份正确 |
| 时间 | 转写对齐误差与采集时钟漂移分别报告 | 既有 209ms 双源漂移不是词级时间戳准确率 |
| 上下文 | 跨片段术语一致性；加入错误术语提示的负例 | 检查是否凭上下文编造 |
| 可用性 | 提问到找到并回听核对的时间、成功/失败数 | 选择产品主题，而非只选最大模型 |
| 性能 | 相同目标机的 RTF、峰值内存、端到端等待、取消完成时间 | 评估本地可用性；RTF 不等于字幕延迟 |

建议硬底线：原始音频/hash 不变、所有引用可解析到准确输入、无越权读取或静默模型回退；持久化和契约变更按项目政策 RED/GREEN。质量提升阈值在基线完成后、查看保留集结果前确定；不能看完结果再改标准。任一安全/来源硬底线失败就停止采用；质量收益不明确则继续使用基线。结构化时间、speaker、置信度相关数据若当前模型不提供，应记录不支持，不靠后处理伪造能力。

产品价值建议沿用“每周成功找回并核对的有效片段次数”，辅以首次记录耗时、重复使用、纠错成本和数据去向理解度。50 个 Session 的找回方式比较、4 周价值日记可作为后续研究规模，当前没有这些研究结果，也没有引入遥测或上传音频。
