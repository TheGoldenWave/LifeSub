# LifeSub 产品现状洞察

> 评估日期：2026-09-09
> 评估范围：0.2.1 已发布能力、0.2.2 规划、当前安装版交互与长期产品方向
> 文档性质：现状评估与建议，不是已批准的新 PRD、发布日期或开发授权

## 一、结论先行

LifeSub 已经完成了一个可信的 macOS 本地音频证据产品闭环：真实录音、分片、ASR、Receipt/Revision/Segment、搜索、回放、导出、诊断和安装包验收均有历史证据支撑。当前差异化基础是原始音频与转写的可定位、可追溯和修订留痕；完整撤回、跨系统授权引用是进一步的产品目标，不能一并视为已交付。

但产品还处在“工程可信度领先于用户价值验证”的阶段。0.2.1 证明了系统能够可靠工作，尚未证明用户会持续使用、哪些场景最有价值、用户是否能理解 Evidence 与 Memory 的边界。下一步应先做轻量稳定化和真实使用研究，避免过早扩展云端、全天候、视觉、硬件或复杂 Agent 能力。

当前还存在三类口径风险：README 仍称其为“个人记忆系统”，与产品定义中的 Evidence 基础设施定位不一致；历史路线图仍保留已被后续记录取代的“真实采集未完成”描述；同一 0.2.1 版本多次重新打包，产品对外需要一个明确的发布身份和变更说明。

## 三、整体版本规划

### 0.2.2：稳定化（建议作为下一版本）

建议严格限定在四类工作：

1. 信息架构：设置、诊断、模型状态的主次层级和可读性。
2. 状态表达：探测年龄、恢复中、失败、未安装、未授权和可录音结论。
3. 操作便利性：重新测试、复制身份、打开系统设置、搜索清除与命中导航、持续播放控制。
4. 基准能力：启动、首帧、RTF、RSS、取消和长列表性能基线。

停止线是“不新增 schema、实体、helper/process 边界、捕获语义、发布语义或验收矩阵类别”。一旦需要其中任一项，应另立版本。

### 0.3+：范围需要重新排序，不能直接按旧版本号启动

8 月 20 日旧路线曾将 0.2.2 定为原生采集、0.3 定为匿名说话人、0.3.1 定为声纹；8 月 16 日另有跨设备 V0.3 计划。后续 0.2.1 已吸收真实采集，0.2.2 改为稳定化。说明版本号已发生含义冲突，0.3/0.3.1 只能视为历史候选，不是当前确认的排期。

建议稳定化后先比较“找回效率、存储与删除、一个真实上层消费闭环、说话人质量”的实际收益，选择一个主要成果作为下一版。匿名分离先于身份匹配是合理依赖，但不等于它们必然先于所有其他能力。

#### 匿名说话人候选（旧计划标为 0.3）

在录音时间戳和 ASR 稳定后，增加匿名 speaker turn、对齐、人工修订和独立 revision。必须先证明失败时 ASR 仍可用，再冻结 DER/JER 质量门槛。

#### 授权声纹身份候选（旧计划标为 0.3.1）

增加多样本注册、质量拒绝、阈值、未知说话人、撤回和删除。声纹只负责身份匹配，不能成为长期记忆或人物档案的权威。

#### 其他后续能力（版本号与日期待定）

包括存储/保留策略、跨设备合并、AEC 派生音频、转写融合、预览与规范化 revision、MCP/Agent 合同和多模态 Source Adapter。每项都需单独 PRD 与真实验收，不以“参考产品有此功能”为立项理由。现有材料不足以给出可信的人日、发布日期或商用时间，本报告不新增排期承诺。

## 四、产品定位判断

### 当前定位

推荐对外统一为：

> LifeSub（旁白）是本地优先的个人音频 Evidence 工具：可靠记录声音，生成可定位、可修订、可导出的转写，并通过授权的 Evidence Contract 提供给上层工作流。

现阶段更准确的承诺是“什么时候、哪个音频来源记录了什么，原始声音在哪里”。产品定义中的“谁”仍依赖未完成的说话人能力，不能承诺自动认人。项目解释和行动属于 Malow，长期事实与知识治理属于 GoldenWave。

### 推荐的第一用户与第一价值

设计规范面向长时间记录会议、讨论和个人口述的桌面用户。建议第一轮聚焦“已经需要复核原话的知识工作者”，尤其是敏感内容希望本地处理、需要给结论附上原始出处的人。这是待验证的优先细分，并非已有用户调研结论。

核心任务可以表述为：“当我参加一次重要讨论，我希望可靠保留声音，事后迅速找到并核对一句话，引用时知道来源没有被悄悄改写。”用户不应先理解 Catalog、Provider 或三个产品的生态架构，才能完成这个任务。

相对会议纪要产品，LifeSub 的机会在核对和来源控制；相对语音输入产品，机会在持续记录与后续找回；相对个人知识库，机会在保留原始证据。当前没有市场访谈、留存、付费或竞品效果对照数据，尚不能宣称形成护城河或产品市场匹配。独立使用时的“记录—找回—核对—导出”必须成立，生态集成才能成为增益。

### 定位需要修正的地方

- README、应用首屏和安装说明应删除“个人记忆系统”作为当前产品定义，避免用户期待自动摘要、自动记忆和自动行动。
- “AI 润色”“声纹库”“快速输入”等能力需要标注为派生处理或辅助工作流，不能让用户误认为它们会改变原始证据。
- “本地 ASR”“模型已就绪”“可录音”必须是三个不同概念：模型可用不代表设备和权限可用。
- 长期 Evidence Fabric 可以作为愿景，但不能在发布文案中暗示已经支持视觉、健康、跨设备或全天候采集。

## 五、交互与设计评估

当前界面遵循冷静、精确、无阴影、锐角、Evidence-first 的设计方向，视觉治理和响应式基础已经成熟。安装版首屏可在数秒内看到录音入口、设备、连接状态和“待检测”结论，时间线也已经能承载真实数据量。

反模板化判断：整体通过；没有装饰渐变、玻璃卡片或夸大的营销数字。但录音首屏仍用较多面积展示准备状态，空笔记面板长期占位；模型列表让运行时、语言和许可与用户选择近乎同权。这是信息优先级问题，无需改变已经确定的深色、克制风格。

本次检查了安装版的录音、设置、ASR、模型、诊断、词典及时间线，没有开启新录音、下载模型、修改设置或删除数据。以下分数是专家启发式判断，不是用户实验、可访问性认证或全路径回归结果。

### 按用户类型的风险

- **首次用户**：看到“本地 ASR · 待接通”会误以为产品核心能力不可用；模型页的“未安装/已就绪”和诊断页的“需处理项”需要先给可行动结论。
- **高频用户**：已有命中跳转和持续播放条；当前大量以时间自动命名的会话仍需要逐条辨认，是否需要手动标题、标签或导航摘要应由找回任务实验决定。
- **可访问性用户**：键盘焦点和 ARIA 基础较好，但颜色不能独立承载“可录音/阻塞”，移动图标导航需要持续保留可理解标签。
- **边界测试用户**：删除、断连、权限撤回、长文本、长列表和重启恢复是产品可信度的核心；这些场景要继续用真实环境证据而非 Demo 覆盖。

## 六、最需要明确的产品问题

### P1：产品到底承诺“证据”，还是承诺“记忆”

这是当前最大口径问题。必须统一 LifeSub 的首屏、README、商店描述和生态说明：LifeSub 记录和整理 Evidence；它不自动生成正式 Memory、Project 状态或行动。

本文 P1 指明显误解或重大体验风险，P2 指可绕过的效率问题，P3 指细节打磨。本次未证实新的 P0 阻断或数据损坏，不因定位争议重新否定既有发布放行。

### P1：首次使用的“可录音”判定

用户需要一个明确结论：“现在可以录音 / 需要打开录屏权限 / 需要测试麦克风 / 当前模型未就绪”。诊断摘要不应把可选模型未安装与当前核心链路阻塞混为一谈。当前实现将所有非 `runtime_qualified` 模型计数，容易把未选择的可选模型误报成阻塞。

实机显示“发现 5 个需处理项”，其中 4 个来自未安装的可选模型，1 个来自系统音频未授权。两个已安装模型仍为就绪。不能要求用户安装全部模型才能让诊断清零；同理，单麦克风模式下也不应把系统音频权限直接算作当前任务阻塞。判断当前所选模式/模型必须取真实配置，不能由前端猜测；若现有数据不足，只改为中性状态汇总，不伪造精确就绪结论。

### P1：默认工作流是导入，还是实时记录

当前实时录音已成为主入口，音频导入仍是重要补录入口，但两者在新用户心智中尚未形成明确分工。建议把产品主任务定义为“记录一次声音并稍后找回”，导入作为“已有音频补录”，不在首屏与实时录音争夺同级注意力。

### P1：转写结果的可信层级

2026-09-11 用户确认：围绕录音忠实度的内容治理属于 LifeSub。用户入口统一为「原始 ASR / AI 校正」，术语修正、说话人归属与背景过滤作为 AI 校正的可勾选维度，不再拆分校正转写与目标对话视图。人工改动和处理来源在差异详情中标注，不要求多个顶层版本入口；不覆盖原始 Revision、不按维度复制全文。正式定义见 [产品定义](product-brief.md)。这是后续能力决策，下述现状缺口仍然成立。

当前有三个具体承诺缺口：

- ASR 设置宣称“点击未知说话人即可保存声纹”，同时“注册新声纹”禁用；实时页重命名函数只更新当前组件文本，没有注册声纹的持久化动作。这需要先纠正文案，正式身份功能另立项。
- 词典页宣称会修正未来 ASR，但 8 月 26 日计划的 Task 16“词典规范化派生 Revision”仍后置。词条可保存不等于改善识别的生产闭环已经验证；应明确当前作用范围。UI 的项目范围还固定为 `project:lifesub`，不能宣称已具备 Malow 多项目上下文。
- 实时页的 AI 润色保存在组件状态，按返回行映射片段；“复制全部”读取原始 `segments`。因此“看见润色、复制原文”的语义需要明说，不能把当前 UI 润色等同于可审计持久 Revision。合并/拆分行后的时间映射属于后续专项验证，本次未运行 LLM 复现。

### P1：录音同意与删除边界

录音状态可见已经实现，但会议/家庭/公共场景的同意提示、保存期限、他人删除请求、导出副本和下游 Evidence Ref 撤回仍未形成产品规则。隐私必须成为操作流的一部分，而不是设置页里的说明。

删除词条、笔记、声纹的接口不等于完整录音删除/撤回产品已完成。本次检查的时间线未见完整录音清理与恢复工作流。建议先列出音频、转写、索引、导出文件、备份和下游缓存的删除边界，再决定恢复期限；这涉及持久化语义，应在 0.2.2 之外设计。

存储也会成为长时产品的实际成本。当前录音设置为 16kHz、16-bit PCM，单源原始负载约 115.2MB/小时，双源约 230.4MB/小时；双源每天 8 小时、30 天约 55.3GB，未计模型、索引、文件头及备份。这是公式估算，不是本轮实测。旧文档中的 Opus 压缩和 retention 不能视为现版已提供。

### P2：统计栏和长期使用反馈是否保留

24 小时统计目前不是查找证据的核心任务，可能增加噪声。应通过真实使用观察决定是保留为轻量运营指标，还是移到独立入口。

### P2：浏览器 Demo 的产品地位

Demo 已明确不会录音或保存，但仍需决定它是开发预览、产品介绍，还是长期的只读样例。若继续保留，首屏应只保留一处免责声明，按钮使用“播放示例转写”，避免模拟真实采集。

## 八、建议的产品指标

当前缺的不是更多工程测试数字，而是用户价值指标。建议从真实用户试用开始记录：

- 首次配置到第一次成功记录的时间；
- 记录结束后 30 秒内能否找到目标片段；
- 搜索结果回到音频的成功率和耗时；
- 原始转写、人工修订、AI 润色之间的误解率；
- 权限/设备错误的自助恢复率；
- 7 日和 28 日内重复记录率；
- 用户认为“值得保留”的 Session 比例；
- 用户是否能正确预测音频、转写、导出和下游 Agent 的数据去向。

建议把“每周成功找回并核对的有效片段次数”作为候选北极星指标，而非录音小时数。定义一次有效找回：用户提出真实问题，定位到带来源的片段，通过回放核对后认为问题得到解答。录得越多不一定越有价值；找到错误片段或只点击结果不算成功。以下都是研究建议，不是已经安排的测试或承诺：

| 实验 | 方法 | 决策用途 |
|---|---|---|
| 首次使用 | 建议 5 位新用户，在干净配置下完成准备、短录音、停止、找回；记录求助点和误解 | 判断 S1/S2 是否足以消除配置成本 |
| 真实价值日记 | 延续开放问题文档：连续 4 周记录会议/讨论/灵感，每周回顾遗漏和再次使用 | 决定音频楔子是否成立、是否需要更多来源 |
| 找回方式对比 | 从自愿提供的 50 个 Session 中比较关键词、导航 Digest 和人工整理；没有 Digest 产品时用受控研究原型 | 测找回时间、命中率和误导率，再决定是否开发摘要 |
| 同意与撤回理解 | 用开始录音、暂停、云端、Agent 读取、删除五种情境，要求参与者预测数据去向 | 冻结隐私行为之前先验证心智模型 |
| 一条生态消费链 | 选择一个真实任务，验证片段引用、人工核对和撤回后的状态表达 | 决定先做哪个消费者，避免同时做三个插件 |

先测基线再冻结改进目标；如试用人数较少，应保留任务记录和个案原因，不用不稳定百分比包装结果。优先本地、自愿研究记录，本轮不引入遥测或外发用户音频。

## 十、总体产品判断

当前最有价值的投资是把“可信的内部事实”翻译成用户能看懂、能采取行动的产品状态，再验证用户是否真的因此更容易找回重要内容。把录音和转写做得可靠已经是重要进展；下一次里程碑应证明“用户愿意再次回来找证据”，而不是继续增加模型、设置或设备数量。
