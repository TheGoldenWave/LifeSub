# LifeSub 测试与审查策略

本文是项目关于测试先行、验收证据和代码审查的单一事实源。`AGENTS.md`、开发/审查 Context、Claude/Codex Agent 角色和 PRD 模板均应引用本文，不得另行定义冲突规则。

## 1. 核心原则

1. 验证方式必须匹配变更风险和可观察结果，不以新增测试数量衡量质量。
2. 行为、数据、安全和接口契约变更采用 TDD：先观察目标测试因当前缺陷正确失败（RED），再做最小实现并验证通过（GREEN）。
3. 纯视觉、文档、配置和生成物变更不得为了形式合规而制造无意义单元测试；必须提供可重复、能发现目标缺陷的对应证据。
4. 混合变更拆分验证：行为部分走 RED/GREEN，视觉或产物部分走截图、构建或结构化检查。
5. 自动化测试不能替代真实环境验收。原生权限、音频设备、安装包、真实模型和重启恢复等能力必须在目标环境验证。

## 2. 变更分类与首选验证

| 变更类型 | 典型内容 | 必需的首选验证 |
|---|---|---|
| 行为与业务逻辑 | 状态机、快捷键、错误处理、导入流程、重试、计算结果 | RED/GREEN 单元或集成测试；相关测试回归 |
| 数据与证据链 | Catalog 写入、事务、迁移、revision、来源/provenance、恢复 | RED/GREEN 集成测试；故障注入；持久化与重启验证 |
| 安全与接口契约 | 权限、身份、输入校验、API/DTO、文件边界、并发 fencing | RED/GREEN 契约或安全测试；负向用例；相关 feature 构建 |
| 纯视觉与响应式 | 布局、间距、字体、颜色、对比度、溢出、断点 | Playwright/浏览器截图；多视口检查；DOM/可访问性检查；必要时视觉基线 |
| 交互可访问性 | 焦点顺序、dialog、键盘导航、ARIA、touch target | 浏览器级交互测试；可访问树或 axe 类检查；关键行为可补组件测试 |
| 文案与文档 | UX 文案、README、PRD、架构说明 | 链接/格式/lint 检查；术语与事实核对；渲染预览（如适用） |
| 配置与生成物 | manifest、CSP、构建配置、Token 生成、脚本参数 | 解析/Schema 检查；生成结果 diff；构建或 smoke test；禁止仅断言字符串存在 |
| 性能与资源 | 启动、内存、RTF、长任务、包体 | 基准测试或量化采样；阈值证据；回归对比 |
| 纯重构 | 无外部行为变化的结构调整 | 现有回归测试先绿；重构后保持绿；必要时补缺失的契约测试 |

若一个问题无法归类，先写清楚它的可观察失败和风险，再选择验证手段。不得默认把所有问题归入单元测试。

## 3. RED/GREEN 适用规则

以下情况必须看到 RED：

- 新增或修复可执行行为；
- 修复数据丢失、伪成功、权限、身份或来源问题；
- 修改状态转换、事务、并发、恢复、错误映射或公共接口；
- 修复已有测试未覆盖的生产缺陷。

RED 证据可以是：

- 新测试因目标缺陷失败；
- 已有测试已稳定复现目标缺陷；
- 无合适测试框架时，可重复的最小复现脚本或命令在修复前失败。

RED 必须因目标行为缺失而失败，不能是语法错误、错误 mock、环境未启动或与需求无关的断言。若测试修复前已经通过，说明测试没有证明该缺陷，应修正测试或重新选择验证层级。

以下情况不强制新增失败单元测试：

- 只改变视觉呈现且不改变交互语义；
- 只修改文档、注释或静态文案；
- 只修改配置、元数据或生成文件；
- 现有自动化测试已能证明目标缺陷；
- 外部生成代码不适合手写行为测试。

不强制单元测试不等于免验证。必须按第 2 节提供可重复证据。

## 4. Spec 与 PRD 要求

新 PRD、技术设计或实施计划的验收部分，应为每类验收条件声明：

- 变更类型；
- 风险级别；
- 验证层级（单元、集成、E2E、视觉、构建、量化或真实环境）；
- 通过标准；
- 必需环境与 fixture；
- 是否要求 RED/GREEN；
- 交付证据路径或命令。

Spec 不得笼统写“补测试”或“所有改动 TDD”。应写明哪个行为需要失败测试、哪个视觉问题需要哪些视口截图、哪个配置需要何种构建/Schema 证明。

## 5. 开发与 QA 工作流

1. 从 PRD/issue 提取验收条件，并按第 2 节分类。
2. 为行为类验收建立 RED；纯视觉/文档/配置类先建立可重复的失败基线或明确检查清单。
3. 做最小修复。
4. 运行 focused 验证，确认目标缺陷消失。
5. 运行相关回归；到达门禁时执行 Tier 2/Tier 3。
6. 保存命令、测试数量、截图或报告路径，不用“看起来正常”替代证据。

QA 不要求每个验收条件都落在 `tests/specs/`。测试应放在最能证明风险的层级：模块测试靠近模块，跨模块用户路径放在 `tests/specs/`，视觉证据放在 `output/playwright/`。

覆盖率阈值由 feature spec 或风险政策明确规定；项目不设置脱离上下文的统一 80% 硬门槛。`skip`/`ignored` 测试必须有原因和触发方式，不能用于隐藏本应执行的失败。

## 6. 审查标准

Reviewer 必须先判断验证手段是否匹配变更类型，再判断证据是否充分。

- 行为类变更没有有效 RED/GREEN 或等价复现证据，可作为 Important；涉及数据、安全、身份或来源时可升级为 Critical。
- 纯视觉变更没有新增单元测试，本身不是 finding；缺少目标视口截图、可访问性检查或出现溢出/重叠才是 finding。
- 文档或配置变更没有行为测试，本身不是 finding；缺少解析、构建、渲染或产物核验才是 finding。
- 不得要求与当前 Task 无关的未来测试，也不得为了覆盖率数字增加只验证 mock 的测试。
- 测试通过但没有证明原始症状，不视为验收完成。

放行仍遵循项目严重级别政策：Critical 必须为 0；Important 按 `AGENTS.md` 的当前规则处理；Minor 记录但不阻塞。

## 7. 项目门禁

- Tier 1：当前行为或组件的 focused 验证。
- Tier 2：focused + related tests、格式、lint/clippy、类型/构建检查和 `git diff --check`；命令以 `scripts/check.sh tier2` 或 `make check` 为准。
- Tier 3：Task 完成时运行全量测试和目标 feature/build；涉及 UI 时加 Playwright 与多视口截图；涉及原生能力时加安装包/目标设备验收。

门禁命令是最低要求，不替代 feature spec 明确的真实模型、音频、权限、性能或重启恢复验收。
